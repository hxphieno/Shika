# 离线拼写纠错

本功能默认用于中文全拼及当前双拼方案。它在原有 Rime 引擎外补充候选搜索，仍由 Rime 完成最终汉字转换、提交和词频学习。实现依据见 [实现前调研](autocorrection-research.md)。

## 行为

- 对词库编码进行一次替换、漏键补入、多键移除、相邻字母交换检索；相邻键替换的成本低于远距离替换。
- 正确完整拼写的前置候选及已学用户词保持原顺序。双拼误按后若恰好也是合法词码，保留其原义，将可能的修正放在后续候选中，不保证所有错键都会自动变为首选。
- 找不到可靠完整匹配时，按编辑成本和原词库词频提供优先纠错候选。空格确认显示首选；Return、标点和切方案先提交显示首选再继续原操作。
- 原始码串始终保留，删除按实际输入删一个字母，点击拼音原码上屏仍输出输入过的字母。取消不产生文字。
- 选择纠错候选时，将正确编码送入真实 Rime 并选择对应汉字，因此用户词频学习发生在正确编码上。原生部分候选与完整纠错候选同字时使用完整纠错路由，防止汉字上屏后仍残留错按字母。
- 已经手动选定句子的一部分后，继续采用 Rime 原生分段处理，不撤销用户确认的汉字来猜测整句。

## 分层与资源

`SKRimeSession` 负责 C API 调用、会话、替换输入及按文字选择候选。`SKRimeEngine` 负责合并原生与纠错候选并维护提交路由。`SKSpellingCorrector` 只做当前方案的编码检索，键盘视图和候选栏无需知道索引实现。

构建时运行 `scripts/generate-correction-index.py`，从既有 Apache-2.0 `pinyin_simp` 词典生成每个方案的排序二进制索引。双拼编码直接读取项目真实生成的 schema 映射，不维护第二份手写键位表。变更双拼方案后应重新运行 `scripts/build-rime-data.sh`，同时更新 Rime prism 和纠错索引。

全拼索引 38,643 个编码、1,217,815 bytes；双拼索引 38,617 个编码、1,106,900 bytes。运行时只加载当前方案，采用映射数据和固定长度记录，词条不会全部展开为 Swift 字符串对象。每次输入只生成一次编辑的有限变体，二分查索引后最多尝试 12 个编码，最多补充 3 个纠错候选。输入码长限制 3–48，显式分隔符不参与自动修改，单字未收入纠错词索引。

Rime schema 增加 `spelling_hints: 64` 与 `always_show_comments: true`，内部用候选规范拼音判断是否完整精确匹配，覆盖用户词。没有打开原生 `enable_correction`，避免重复搜索及原生邻键层对原有简拼的副作用。

所有资源随应用安装，全程离线，不需要完全访问，也不发送用户输入。没有新增第三方词库、GPL 脚本或语言模型。

## 验证入口

```sh
bash scripts/test-autocorrection.sh
bash scripts/test-autocorrection-interactions.sh
bash scripts/test-autocorrection-independent.sh
bash scripts/test-input-session.sh
```

第一项是实现前固定的 320 组语料：每方案 100 错误、40 正确、20 边界，按原词划分 development/heldout。原始边界里“略”的双拼编码写成了全拼 `lve`，实现过程中核实真实键位后修正为 `lt`；没有删除困难样例。

独立 agent 另外冻结了 400 组（每方案 40 正确与 160 错误），原词与 320 组不重叠。排名阶段不选择候选，baseline 和纠错在新进程、新 userdb 中分别测试；上屏交互另外运行，避免先学习测试答案再测排名。

32 项专项交互验证四类错误真实上屏、空格/Return/标点、原码、删除、取消、分页、切方案、部分选词和新用户词保护。原有 48 项会话验证及跨进程词频学习回归同样运行。

完整结果见 [纠错验证记录](autocorrection-validation.md)。

## 能力边界

这是一套轻量离线拼写容错，不是 Gboard 的上下文神经解码器或通用语法纠错。多个错误、词库外的新词、人名歧义、极短双拼码和任意长句中的错误仍可能无法给出目标词。学过的用户词能正常保留、排序，但只读纠错索引不自动收录词库外用户新词的所有错拼形式。不会因词频高而强行覆盖合法完整输入；因此“目标在前三候选”与“目标自动成为首选”必须分别报告。

## 运行时稳定性

生产引擎在 iOS 26.5 Simulator UIKit host 中完成 300 次交替方案与 1,687 次逐键输入，功能断言零失败，每键 P95 7.54 ms。第 120→300 次 `phys_footprint` 净变化为 −49,152 bytes，保持约 34.9 MiB 平台，通过原 8 MiB 增长门槛。首次较短实验的门槛失败和分离诊断完整保留，详见 [运行时验证](autocorrection-validation.md#最终-300-次运行结果与独立复核)。

此项用于确认当前压力负载下没有随切换持续增长；UIKit host 的总内存、截图渲染开销、实际键盘扩展内存和物理 iPhone 表现分别解释，不能互相替代。
