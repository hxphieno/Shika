# 第二轮底层优化：学习覆盖与搜索成本

日期：2026-09-26。基线 `c885466`；继续只改 Engine，不改 UI、Core 输入策略、布局、Return、空格或删除的语义。其他任务的主应用、图标、工程文件与声明文件修改未纳入本轮提交。

功能提交：`d1827dd`（双拼搜索剪枝），`9021155`（全拼已学词纠错与存储上限）。研究、被否决的实验和最终证据另行提交。

## 社区方案与实验选择

| 方向 | 参考及判断 | 本轮处理 |
| --- | --- | --- |
| 更少的错拼枚举 | [SymSpell](https://github.com/wolfgarbe/SymSpell)通过删除索引减少候选生成，但需要预计算和额外索引；其英语基准不能直接套用本项目 | 实验缩小查找范围及提前跳过不可能的双拼编辑分支，只保留后者 |
| 用户历史也参与纠错 | [Mozc UserHistoryPredictor](https://github.com/google/mozc/blob/master/src/prediction/user_history_predictor.cc)把用户历史作为独立、有容量约束的候选来源；[参数接口](https://github.com/google/mozc/blob/master/src/protocol/commands.proto)单独控制历史纠错查询 | 不移植整个 Mozc；复用现有已学词索引，将恢复能力推广全拼，并由 Rime 核实完整读音 |
| 增加长句候选 | [librime 1.17 ScriptTranslator](https://github.com/rime/librime/blob/1.17.0/src/rime/gear/script_translator.cc)、[Poet](https://github.com/rime/librime/blob/1.17.0/src/rime/gear/poet.cc)支持控制整句枚举和截断 | 单独实验放宽句子截断参数，因质量回退而放弃 |
| 提高纠错排名 | [librime #1120](https://github.com/rime/librime/issues/1120)有纠错权重干扰正常输入的用户反馈；这是风险案例，不是适用于所有键盘的结论 | 不做未经校准的全局纠错提权；已有准确候选保护不变 |

SymSpell只做了结构容量估算，没有实际移植，也不声称测得其性能。当前两索引各约96万个编码。按长度7前缀、一次删除粗算，未合并重复的posting ID本身约28/31MB，尚不含键和索引结构；去重可能减少这些数字，不能视作实测内存下限。这个估算尚不足以证明移动键盘收益，因此没有添加新索引或库。明细见 `evidence/backend-round2/symspell-sizing.json`。

## 保留一：双拼先排除不可能的编辑类型

双拼完整词典编码必为偶数字母数。原实现先生成所有替换、交换、插入和删除变体，再检查奇偶数；新版在分配字节数组之前跳过不可能的编辑类型：偶数输入只查替换/交换，奇数输入只查插入/删除。合法音节检查、词频、距离权重、排名和候选数量均保持。

冻结2629个去重输入，涵盖已有全拼/双拼样本、0–64长度边界、固定随机输入、非字母与显式分隔符。逐词测试所有前缀及重输，**46358条编码/文本/编辑成本/词频签名全部相同**。使用单调时钟，各词新建corrector，区分首次查询和立即重输，三轮采样。

- 第一组双拼冷查询累计2566.8→1981.0ms，减少22.8%；P95 0.1884→0.1749ms。
- 控制运行顺序的复测先新版后旧版，同1542个双拼输入：累计旧2503.5、新2078.0ms，减少17.0%；P95旧0.1905、新0.1738ms，签名仍全部相同。
- 全拼查询路径不变，首轮P95约0.8135ms保持一致。以上均是拼写索引函数耗时，不是整个键盘响应提速比例。

另测试了一字母和二字母前缀区间索引，400条筛选实验未得到稳定冷查询收益，最终生产代码没有保留这两种索引。原始报告保存在 `evidence/backend-round2/search/`；较大报告无损压缩为JSON gzip。

## 保留二：全拼已学新词的错拼恢复

原版 Rime 能学到全拼新词，但静态纠错索引不含新词，新词错码往往没有完整可用的候选。现在复用有界学习元数据，按全拼与双拼分文件保存；全拼完整上屏后，额外查询原生 Rime，只有目标文本和完整读音都一致才记录。这样四字母简拼也不会被误认为完整读音。原码 Return、取消、浏览和未提交的部分选词均不记入。

全拼支持一次替换、漏键、多键或相邻交换，最多查询4条已学建议，再由 Rime 校验词语及完整拼写，最终上屏与词频学习仍由主会话负责。没有新增另一套词频模型，没有导入旧历史，没有对日文或混输启用该索引。旧双拼文件和用法兼容。

独立 agent 在看新结果前冻结8个人工三字新词及32个错码，核实新词不在静态词典；这些是学习功能的受控数据，**不是自然输入准确率样本**。两版通过真实候选选择学习相同词语，然后另一个进程先统一查询错码，再选择候选：

| 指标 | 原版 | 新版 |
| --- | ---: | ---: |
| 8个新词精确输入学习恢复 | 可用 | 可用 |
| 32个错码中出现目标文字 | 1 | 32 |
| 32个错码完整上屏且清空、不重复 | 0 | 32 |

原版唯一同文字结果实际是部分候选，选择后没有完整提交，未算作成功。最终全拼专项 **238/238**（学习99、跨进程115、关闭纠错16、索引边界8），双拼专项回归 **117/117**。独立报告与原始观察见 [独立验收](backend-round2-independent.md)。

### 验收发现并修复的容量问题

首轮按“最多512条”限制，48个扩展区汉字的边界记录使用四字节UTF-8，文件达到134145 bytes，超过自身131072 bytes读取上限，导致重启无法恢复。首轮index测试6/8的失败记录保留。

最终改为同时满足最多512条与128KiB的写入字节上限；必要时淘汰最旧记录，再原子写入。同一极限测试最终保留最新500条，131001 bytes，重启成功。没有通过放宽读取上限掩盖问题。双拼正常最大长度记录仍可保留512条。

### 成本与限制

在新用户目录反复选择6个固定词，每版240次实际提交全部正确。预先限定全拼选词P95增加不超过2ms、总P95不超过10ms：测得0.024→1.288ms，增1.264ms；双拼1.209→1.255ms。macOS峰值RSS40.34→41.09MiB。此计时是在字节容量修复前的学习实现采集的；短词不会触发容量淘汰分支，最终代码另做功能与模拟器验收，不能把这份计时当作最终源码逐字节完全一致的基准。

新增成本主要出现在选词后的完整读音核验和本地持久化。未做手机实测，不将这些macOS数字当作手机体验保证。升级前的全部历史新词不会被自动导入；索引会随新的有效选词逐步积累。

## 放弃：仅放宽长句截断参数

独立查证：librime 1.17的多个句子枚举在没有Octagram模型时也能运行，空grammar走词条权重的回退评分；不能因为没有模型就断言这些参数无效。已有配置是5个句子、8个同音词、截断0.01。实验只将两个主方案的截断改为0.05，辅助schema不变，并实际读取运行时配置核对。

36个新句子与既有测试目标无重合，逐句预先固定读音；句子由agent编写，其中锚点词给出固定社区词源出处，不冒充网络自然语料。加上264条既有开发输入，共336条：新句双拼/全拼各自Top5均30/36，未改善；原开发集双拼Top5从84降至78，全拼84降至77。更多整句挤后了部分纠错候选，17个目标排名下降、没有目标排名改善。因此此参数没有合入，也未围绕这些失败继续调参。两版新句全部60个完整命中分别独立提交60/60通过。

这次实验支持的结论是：单纯增加长句候选不足以解决当前长句质量。更好的上下文评分仍值得后续研究，但本轮没有新增上下文模型或宣称长句质量已提升。
