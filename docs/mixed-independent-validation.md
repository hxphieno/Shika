## 发现并由主 agent 修复的问题

1. **组合中的日文长音未进入混输引擎。** 混输引擎接受 `-`，但输入策略把 UI 的 `ー`/`-` 当直接标点，提前提交组合。修复后，`ko`、`ー`、`hi`、`ー` 保持原始组合 `ko-hi-`，可选“コーヒー”；闲置状态仍直接输入这些符号。
2. **候选扩展按文字去重丢失不同消费范围。** `ni'` 的完整“你”和部分“你”文字相同，但前者提交并清空，后者保留组合 `你'`。引擎原本保留两项，会话扩展却丢掉后者。增加可选的消费长度元数据后，两项均可通过扩展候选到达；纯模式原先的去重规则保持不变。
3. **显式中文拼音分隔被抹除。** 旧混合词查询把 `xi'an` 当成 `xian`，产生单音节“先/现/线”候选。修复后独立用例确认“西安”仍可选，这三个跨越显式分隔的单音节词不再出现。

## 架构审查范围

`SKConversionEngine` 只路由模式；混输自管原码、锁定段、候选和本地学习；解码器处理分段与语言成本；中文词索引只做只读边界查询。消费长度来自 ASCII 原码，未使用输出文字长度。纯中文和纯日文继续由各自引擎处理。

最终片段精排在联合边界搜索后进行：最多考察 6 条路径、最多查询 4 个不同中文连续片段，并复用引擎内缓存，不是每个子串都创建 Rime 会话。混输没有引入 UIKit 依赖。候选消费长度是可选元数据，纯引擎仍使用原有默认构造；会话按文字与消费范围共同去重，UI 无需承担语言或分段判断。本轮审阅未发现新的阻断性输入完整性缺陷。

## 最终质量报告的独立复核

已审阅 `Tests/MixedEngineChecks.swift`、`scripts/test-mixed-engine.sh`、`scripts/summarize-mixed-quality.py`，并独立从 `docs/evidence/mixed-engine/final/16.json` 重算主要计数。

- 250 项的排名遍历在任何选词行为检查之前执行；每个用例先 clear，脚本生成新的用户目录。排名循环只输入、枚举和翻页，不选词、不提交，因此不先用测试答案训练词频再打分。
- 新引擎命中要求候选文字属于预先定义的 `expected`，且 `consumedInputCount` 等于**完整输入长度**。没有把只覆盖前缀的同文候选记作整句成功。旧基线没有此元数据，以 nil 兼容；新混输引擎每项都提供消费长度。
- 汇总保留所有失败分母，不将未命中的 rank 0 排除。冻结语料的开发/保留划分与预期答案没有在此汇总阶段修改。
- 144 条保留混输用例：Top1 为 **112/144（77.8%）**，Top5 为 **128/144（88.9%）**，Top10 为 **132/144（91.7%）**。250 条整体没有非预期提前上屏。
- 54 条保留的纯语言控制句在**混输模式**下 Top5 为 54/54。这个分组不能单独证明纯中文、纯日文模式完全没有回归；独立行为测试另外检查了这些模式的路由和基本转换。

这些用例是作者设计、公开词源改编及少量来源摘录改编的冻结语料，**不是自然用户输入分布的随机样本**。同一词族分组隔离、固定预期和不训练后打分提升了可比性，但不能将 88.9% 或 91.7% 当作日常使用成功率。

### 保留失败及其含义

保留混输有 16 项未进入 Top5，其中 4 项在第 6–10 位，12 项未进入 Top10；原始失败均保存在 `final/failures.json`。按实际候选观察，主要问题是：

- 中文同音字与句子排序，例如“再喝→在和”“坐→做”“订→定”“真香→真想”。部分正确整句仍在更后面。
- 语言边界或同码竞争，例如 `pan` 偏向“盘”而非“パン”，`gacha` 偏向“嘎查”，`oshi` 被中文片段解释；多次混合时还会连带影响中文切分。
- 新词、片假名/平假名偏好和较长中文片段仍有召回/排序不足。仅凭前十候选不能把某个缺失目标全部归因于词库缺词，因此不作更强的根因断言。

这属于仍需继续提升的候选质量，不等同于本轮已通过的消费长度、提交和编辑正确性。
