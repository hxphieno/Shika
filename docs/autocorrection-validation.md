# 纠错验证记录

日期：2026-09-25。纠错的实现、限制和复跑方法见 [功能说明](autocorrection.md)，实现前选择依据见 [调研](autocorrection-research.md)。

## 独立验收优先结论

独立 agent 在实现者未读取原词的情况下冻结了额外 400 例测试。最终错误样本中，全拼首选命中 **84/160（52.5%）**、前三 **133/160（83.1%）**；双拼首选 **65/160（40.6%）**、前三 **119/160（74.4%）**。80 例正确输入的首选全部保持无纠错基线，零回退。

独立提交阶段，能选到目标的 339 例均实际提交正确文字一次并清空预编辑；61 例没有目标候选，完整保留为未解决，不计通过。首次发现的 15 例“有候选却只提交部分文字、剩下错码”已通过通用候选路由修复，未添加测试词特判。

完整分型指标、首次失败、最终原始记录和源码 hash 见 [独立验收报告](autocorrection-independent-validation.md)。不能用下面较容易的自有数据集成绩代替独立保留集准确率，也不能把前三命中称作自动首选成功。

## 功能和回归

[32 项专项交互日志](evidence/autocorrection/interactions.txt)使用生产 Swift 输入会话和真实 Rime，覆盖：

- 两方案四类错码实际点击汉字上屏，不只检查字符串存在。
- 空格、Return、标点、数字、大写字符、方案切换遵循显示首选。
- 删除真实错码、原码提交保留输入、取消不提交。
- 原生分页索引、纠错分页往返、部分选词后续写。
- 分段选字创造用户新词，并保护新词的精确输入首选。

原有 48 项真实会话断言、100 次连续输入与跨进程词频学习回归均通过。测试不涉及替换候选栏 UI。

## 延迟、内存与解释范围

320 例最终资源的 Mac 优化构建，每键 P50 0.80 ms、P95 6.51 ms、最大 48.61 ms；同次 baseline P50 0.14 ms、P95 1.62 ms、最大 12.17 ms。另一次相同代码的 P95 为 5.47 ms；并行编译高负载时曾超过 30 ms。独立 400 例最终 P95 为 13.56 ms，详见独立报告。这里包含 Rime 转换和纠错检索，明确是 Mac 进程数据，不能称为物理 iPhone 测量。

只读索引全拼 1,217,815 bytes、双拼 1,106,900 bytes，运行时仅持有当前方案的索引；这只是资源体积，不代表整个扩展的常驻内存。实际键盘扩展的截图、设备输入与内存验证由主任务另行记录。

合法完整拼写会保留原首选，所以“双拼错误碰巧形成另一个合法词码”有意不会总被强制更正。一次编辑范围以外、词库外整词、用户新词的模糊检索、多处错误及任意长句中的错误仍有失败；这些边界没有通过删测试或改目标来掩盖。

## Simulator 运行时压力检查

新增 `Tests/AutocorrectionRuntimeChecks.swift` 可通过现有 UIKit host 脚本执行：

```sh
SHIKA_SMOKE_SOURCE=Tests/AutocorrectionRuntimeChecks.swift \
SHIKA_SMOKE_TIMEOUT=180 \
python3 scripts/test-keyboard-simulator.py booted
```

它读取当前进程 `TASK_VM_INFO.phys_footprint`，记录引擎初始化前后、交替方案输入/提交至 300 次，以及释放会话后的内存；前 120 次保留为启动阶段，120–300 次检查点用于观察是否继续增长；仍用原来的 8 MiB 增长、12 MiB 跨度门槛。输出 `runtime-report.json`、四张真实键盘候选/上屏截图和 `result.txt`。每次运行使用新 userdb，不能靠旧学习记录通过候选断言。

这项是生产引擎与键盘视图的 Simulator UIKit host 验证：内存含 UIKit host、Rime 全局缓存和当前方案索引。它既不是物理手机，也不是扩展进程内存；实际扩展应另行测量。压力样本只用于内存保持和操作时延，不参与上面的准确率统计。默认脚本未开启 Swift 优化，报告明确标记这一点。

### 第一轮内存门槛失败后的定位

[首轮原始报告](evidence/autocorrection-runtime/first-run/runtime-report.json)不删除：20→120 次 footprint 增长 14,614,648 bytes，触发原 8 MiB 门槛。曲线同时显示 80→120 次只增长 49,152 bytes、100→120 为零，因此不能只根据前段增长判定持续泄漏。释放会话后没有立即下降，也不能单独证明对象仍被持有；Rime 进程全局缓存和系统分配器会保留已分配区域。

先完成 [Mac 分离实验](evidence/autocorrection-runtime/memory-isolation/)：两个生产 Rime 会话仅切方案、仅查询提交、销毁重建；Swift 只重载索引、重载加检索；完整引擎纠错。各跑 500 次，均在热身后平台，未复现随次数持续累积的对象。对照不是 Simulator 的替代证据，只用于排除明显的会话/索引生命周期问题。未因首轮失败修改生产引擎或放宽阈值。

后续压力实验延长至 300 次：保留每 20 次的全曲线，同时单列原来的 20→120 增量与新增 120→300 增量。稳定性仍按相同 8 MiB/12 MiB 门槛判定，用更长观察区间区分启动高水位和持续增长。截图逐张放在 autoreleasepool 中，并在下一 runloop 再采样 UI footprint，避免将截图 renderer 的临时内存当成引擎内存。

### 最终 300 次运行结果与独立复核

[最终原始报告](evidence/autocorrection-runtime/final-run/runtime-report.json)及 [PASS 结果](evidence/autocorrection-runtime/final-run/result.txt)已保存。本次无生产引擎改动，延长观察后通过相同稳定性门槛：

| 指标 | 实测 |
| --- | ---: |
| 交替方案次数 / 逐键事件 | 300 / 1,687 |
| 引擎初始化 | 68.91 ms |
| 逐键 P50 / P95 / P99 | 2.84 / 7.54 / 9.15 ms |
| 逐键最大 / 方案切换 P95 | 10.38 / 6.36 ms |
| 初始化前 / 后 footprint | 23.02 / 25.27 MiB |
| 第 120 / 300 次 footprint | 34.91 / 34.86 MiB |
| 120→300 净增长 / 区间跨度 | −49,152 / 49,152 bytes |
| 释放会话后 footprint | 34.72 MiB |
| UI 截图后、下一 runloop footprint | 49.14 MiB |
| 功能错误 | 0 |

独立复核全部采样：120、140、160、180、200、220、240、260 次均为 **36,604,136 bytes**，280 与 300 次下降为 **36,554,984 bytes**。这支持“本负载热身后平台稳定”，未观察到随切换持续累积；不能外推为任意文本、无限用户词或所有设备绝无泄漏。首轮的启动区间门槛失败继续保留，并未通过提高阈值使其变成通过。

最终轮的 20→120 启动增量为 2,097,176 bytes，与首轮启动阶段不同，也说明短启动窗口容易受进程分配状态影响。初始化前后约 2.25 MiB 的增量只描述该 UIKit host 当时的差值，不能当作 Rime 的完整内存预算。UI 后数值还包含键盘视图、系统字体、图层及渲染缓存，不能全部归给引擎。

已人工查看候选与上屏截图，确认错码 `zhnogguo` 上屏“中国”，双拼 `niihc` 给出“你好”候选，累计上屏“中国你好”。截图由生产键盘视图与文本代理生成，见 [全拼候选](evidence/autocorrection-runtime/final-run/runtime-pinyin-candidates.png)、[全拼上屏](evidence/autocorrection-runtime/final-run/runtime-pinyin-committed.png)、[双拼候选](evidence/autocorrection-runtime/final-run/runtime-shuangpin-candidates.png)、[双拼上屏](evidence/autocorrection-runtime/final-run/runtime-shuangpin-committed.png)。这些 `CALayer.render` 功能证据不用于验收系统材质的视觉还原；材质比较采用主任务的实际屏幕截图。

**环境界限：**上述数据是 iOS 26.5 Simulator 中、未开启 Swift 优化的 UIKit host，运行生产引擎和键盘视图。它不是键盘扩展进程的 footprint，也不是物理 iPhone 的时延或内存实测。主任务的实际扩展交互证据另行记录。
